# Material rendering rebuild

The former material presets and their overlapping WebGL highlight, SVG surface, native region and per-material CSS effects have been removed from the active interface. The neutral interface keeps theme accents and optional Windows backdrop blur. Existing progress/connection shape and gradient choices remain independent. Saved old material preferences are retained but have no visual effect.

`tools/lab/webgpu-materials/` is a standalone WebGPU geometry and shader experiment for six reference styles. Serve the directory over localhost and open it in a WebGPU-capable browser to try it. It draws a synthetic background, not the desktop. It has not been integrated into the application and is not a finished material implementation. Device, shader and browser compatibility, appearance, performance, scaling, and screenshots must be checked on Windows x64.

A second, native experiment in `tools/lab/native-glass/` uses Direct2D paths, gradients and a resizable Win32 window; it requires only Windows graphics APIs at runtime. Its six shape variants are early geometry experiments, not the approved finished designs. It draws an opaque background and is not connected to the application or the Windows host backdrop. Windows CI compiles it and checks path construction; real-device visual and compositor testing remain necessary. Direct2D may select a software fallback; actual hardware usage needs verification on the target Windows machine. Direct3D plus DirectComposition remains a possible next step for custom shaders and compositor integration, and Skia is another candidate.

A separate Windows 11 Composition host-backdrop experiment is under `tools/lab/native-glass/backdrop.cpp`; it does not capture the screen or yet integrate with WebView2. Its first Windows Server 2025 runner screenshot showed a black client area rather than a visible backdrop. The runner reports transparency enabled and a Microsoft Hyper-V virtual display adapter. The cause is not established; device, compositor and implementation differences still need investigation on a physical Windows GPU. A second capture with a colored reference window behind the test was also black, confirming that the sampled backdrop was not visible on this runner. A user-provided Windows 11 screenshot of the standalone lab showed the wallpaper through the host-backdrop window on their machine. The Windows 11 host-backdrop attribute requires build 22000 or newer, so Windows 10 needs a fallback.

A development-only integration now attempts to paint a Water Bubble background on the native HWND of a real download window. Launch the Tauri process with `MHG_EXPERIMENTAL_WATER=1` and use the desktop background mode. The UI enables the transparent surface only if native initialization succeeds, otherwise it keeps the normal background. The experiment is restricted to download windows, follows the current accent and light/dark selection, and creates/cleans up resources on the window thread. It does not capture the screen. Direct2D paints an opaque background: true Windows desktop backdrop, curved native window clipping, and correct WebView2 composition remain unverified. The native review workflow has an optional `experimental_water` switch that enables the experiment and captures both the WebView and desktop for manual review; a capture failure is recorded explicitly. The corrected review brought the real download window forward and confirmed that the native surface is visible, but it was opaque and showed rectangular corners outside its curved outline. An experimental matching HWND region now removes the rectangular corners and follows resizing. The first real-window capture of the clipped surface cut into the close and Cancel controls; a safe content inset was added. A later Windows runner capture showed those controls inside the outline, and region checks passed at 880×500 and 600×400 logical pixels. Other DPI settings and physical hardware still need visual verification. Native window regions have hard pixel edges, so they do not guarantee the antialiased mockup appearance. Do not treat the experiment as a finished material or ship it as a selectable style without Windows visual and interaction tests.

A second experimental backend now uses a Direct3D 11 device and compiled HLSL shaders in the real progress HWND. Enable it only for development with both `MHG_EXPERIMENTAL_WATER=1` and `MHG_EXPERIMENTAL_RENDERER=d3d11`. It creates one rendering backend, not an additional surface over Direct2D; it prefers a hardware adapter and falls back to WARP. It shares the experimental water outline and clipping with the Direct2D path. A Windows runner review initialized this backend in a real download window and the desktop capture showed the shader under the controls. The capture is still an opaque and rough prototype: no live desktop sampling, refractive material, final visuals or physical GPU confirmation is present. Successful compilation or a WARP run cannot establish hardware acceleration or visual fidelity. A Windows native-review input chooses this backend for separate testing. A Windows x64 smoke test creates its device, swap chain and shaders and exercises a resize; this may use WARP and does not establish visual fidelity.

An additional development-only path now attempts to combine a Windows 11 host-backdrop brush with a premultiplied-alpha Direct3D composition swap chain in the download HWND. Enable `MHG_EXPERIMENTAL_WATER=1`, `MHG_EXPERIMENTAL_RENDERER=d3d11` and `MHG_EXPERIMENTAL_HOSTBACKDROP=1`. The shader receives the existing theme accent, accent strength and surface opacity settings; this connection still needs Windows visual validation. If host composition creation fails, it falls back to the opaque Direct3D path; the DOM reports `data-native-water-backdrop=host` or `opaque` for test diagnostics. Host initialization alone does not prove the backdrop is visible (the virtual runner previously showed black). The host brush is not exposed to the Direct3D shader as pixels, so this path does not yet provide physical refraction or match the target art. A Windows runner review initialized the host composition and passed the original transfer checks, but its virtual display cannot establish real backdrop visibility. The isolated portable review disables browser-host registration and uses separate temporary data; a Windows run verified the browser-host registry entries remained unchanged and produced an experimental portable artifact. The experimental host path sends the real download panel bounds to the same Direct3D pass for rounded panel shading, keeping WebView controls interactive above it. The first flexible-layout review showed the details being compressed and the content overflowing; the corrected layout passed metadata and control-region checks at 600×400 and 880×500 on the Windows runner. The resulting graph was too tall, so the experimental window now starts shorter and caps graph height. Panel-bound updates are serialized, and the review checks that the native renderer receives new bounds after resizing. These changes still need Windows and physical-GPU validation before enabling them in the product.

## Architecture to investigate and build

* A single GPU composition pipeline should own each window's background, silhouette, bevels and material-specific surface geometry. The same geometry must govern clipping and interaction, so an extra rectangular layer does not extend over rounded or faceted edges. Keep controls and text readable above it. Derive tint from the selected accent once.
* Build Water Bubble as a vertical slice: deformable outline and smooth specular edges; then Ice Edge, Smoked Crystal, Frosted Layers, Aero Gloss and Prismatic Glass each need their own authored geometry and shader parameters. The generated reference images are visual targets, not implementation assets.
* Keep progress shapes and colors independently selectable, and connect the existing engine-driven indicators and transfer graph. A shape that follows a material can be a preset without forcing it.
* Prototype Windows Composition host-backdrop and Direct2D/Direct3D integration with Tauri's WebView2 window before committing to a production compositor. A compositor backdrop brush and a CSS backdrop filter are not proof that arbitrary desktop pixels are available to a shader. Direct2D exposes displacement effects, but feeding a real desktop backdrop into them alongside WebView2 needs a Windows prototype. Do not silently capture the screen to fake refraction.
* If desktop capture is needed, obtain user consent and investigate capture exclusion, recursion, protected content, mixed DPI, monitor changes, device loss and resource cleanup. Provide a clear fallback. Test both Windows 10 and 11 x64 where supported.
* Verify all windows, both light and dark modes, accent choices, resizing, text contrast, hit testing, GPU fallbacks and real download behavior on Windows. Compare screenshots directly with the references; a successful installer or shader compilation does not establish visual fidelity.
